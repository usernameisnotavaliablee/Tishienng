## 1. classes.dex 加固结构精确测绘（任务 A-1）

### 1.1 dex 头与 map_list（脚本 `probe_dex_structure.py` 实测输出）

```
file size           = 45352584 (0x2b40688)  ← 实际文件大小
magic               = dex\n035\0             ← 合法 DEX035 头
header.file_size    = 45352584               ← 被改写成=实际大小（容纳夹带数据）
header.class_defs   = 4                       ← 整个 dex 只定义 4 个类（壳）
header.data_size    = 18180 (0x4704)          ← 真正 dex 数据区仅 18KB
header.map_off      = 0x707c
```

map_list（16 项，全部合法）最后一项 `MAP_LIST @0x707c`，**所有合法 dex 结构在 `0x7140` 处结束**。
那 4 个类即此前已知的壳：`com.stub.StubApp` / `com.tianyu.util.{Configuration,DtcLoader,a}`。

→ **从 `0x7140` 到文件尾 0x2b40688 共 45323592 字节（43.2 MB）= dex 合法结构之外的【夹带数据区】**，这才是被加密的真业务 dex 容器。

### 1.2 夹带区是「自描述容器」——找到了长度字段

夹带区头部 12 字节（`0x7140` 起）：
```
0x7140: 71 68 00 01  3d 95 b3 02  dc 04 00 00
        └u32=0x1006871  └u32=0x2b3953d  └u32=0x4dc(1244)
```
其中第二个 u32 `0x2b3953d = 45323581`，正好 ≈ 夹带区总长度（45323592 − 11 字节对齐）。
→ **证实 360 容器是自描述的**：头部带"容器总长度"字段，后面跟分段索引。这解释了为什么 `file_size` 被精确改写——加固器需要知道在哪里停下。

紧随其后（`0x714c`起）是 **XOR 轻混淆的元数据/索引区**：字节直方图里 `0xc6` 出现 453 次（4KB 内最高频），是 `0x00`（长度字段的高位零字节）在 XOR 下的密文 → **元数据 XOR key 字节 ≈ 0xc6**。用 0xa6 解能看到夹带的 ASCII 片段 `7418FDAAB59B1C0C`（与 `.jgapp` 同值）+ `activity` / `com.bx` 等类名残片（脚本 `probe_blob_cipher.py` 实测）。但这是非线性多字节流密码，不是单字节常量，元数据无法用一个 key 全解。

### 1.3 熵剖面：分段压缩+加密容器（非单块 AES）

64 段香农熵（`probe_dex_structure.py`）呈现明显的**周期性结构**：
```
0x7140       8.00  ← 满熵（加密/压缩正文起点）
0x160dea     1.43  ← 极低熵（索引/填充/对齐区）
0x20dc3f     1.49  ← 极低熵
0x3678e9     5.71
...           5~6   ← 大量 5-6 熵（zlib 压缩后再轻加密的 class 片段）
0xc2f33a     8.00  ← 又一个满熵峰
0xcdc18f     1.69  ← 又一个低熵谷
...（这种 [满熵峰→5-6平台→低熵谷] 的模式重复约 6-7 次）
```
→ 这是 **360 自有的「分段（per-chunk）压缩 + 加密」容器**：每个原始 class/dex 片段单独 zlib 压缩再加密，段间有低熵的长度/偏移索引。**不是单一 AES blob**，所以即使拿到一个密钥也只能解一段。

### 1.4 魔数扫描：内嵌 ELF/PK 全是「假阳性」

`probe_dex_structure.py` 在夹带区扫到 2 处 `7f 45 4c 46`(ELF)、6 处 `PK\x03\x04`：
- ELF @0x24380e3：`ei_class=89`（合法只能是 1/2）、`e_machine=10`（非 ARM/AARCH64），**字段全是垃圾 → 落在加密正文里的偶然字节，不是真 ELF**。
- 大量 zlib 魔数（`78 9c` 167 处、`78 01` 1769 处等）也多为高熵密文里的偶然命中，无法从任意一处 inflate 出有效数据。

→ 真业务 dex **没有以明文/可直接 inflate 的形式藏在夹带区**，必须经 `libjiagu` 运行时解密。

## 2. 逆 libjiagu（任务 A-1：判断算法/密钥来源）

### 2.1 ELF 被刻意破坏（反静态分析）

`readelf -S assets/libjiagu_a64.so`：节头表被全部改名为 `..dynamic`、类型错乱（STRTAB/DYNSYM 大小被改成 0x10/0x48）、`nm -D` 报 `<corrupt>`、`strings`（MinGW 版）对它输出 0 行。
→ 这是 360 对自己运行时库的**节头混淆**，常规工具失效。用 Python 正则强抽字符串才拿到内容。

### 2.2 还原出的多阶段加载架构（关键字符串作证）

从 `libjiagu_a64.so` / `libjiagu.so`（v7a）抽出的字符串拼出完整链条：

```
JIAGU_FILE_PATH / JIAGU_ENCRYPTED_DEX_NAME / JIAGU_APP_NAME / JIAGU_SO_BASE_NAME / JIAGU_HASH_FILE_NAME
  → 加固运行时的配置项（被加密 dex 的路径/名/校验 hash）
Protect_enc.so / libjiagu_vip_enc.so / libijmDataEncryption_enc.so
  → 【二级加密 SO】：真正的解密器本身是加密的，运行时先解出来
inflate / inflateInit_ / inflateInit2_ / inflateEnd   (来自 libz)
  → zlib 解压（对应 §1.3 的「压缩」层）
mprotect / mmap
  → 把解出的代码页改成可执行（典型脱壳/自解密行为）
_ZN10DynCryptor9__arm_c_0Ev  →  C++ 符号  DynCryptor::__arm_c_0()
  → 【核心解密类 DynCryptor】，__arm_c_0 是它的解密入口
RMUTGF_KEY
  → 加固内部密钥常量名（密钥本体在二级 SO 里，静态拿不到明文）
java/lang/System , com/stub/StubApp
  → JNI 回调 StubApp（壳入口），完成 InMemoryDexClassLoader 加载
libmono.so
  → 兼容 Unity/mono 的标记（说明这是 360 通用加固模板）
```

**判定**：解密算法是 360 私有的 `DynCryptor`（运行时从 `Protect_enc.so` 解出后才存在于内存），密钥 `RMUTGF_KEY` 也在二级加密 SO 内。**静态环境下既拿不到算法实现也拿不到密钥本体**，所以离线解 dex 不可行——与预期一致。

## 4. classes.dex 离线解密：明确卡点与所需条件

**为什么静态解不出（实锤）：**
1. 解密器 `DynCryptor` 实现位于运行时才解出的二级 SO `Protect_enc.so`，磁盘上是加密态。
2. 密钥 `RMUTGF_KEY` 同样在二级 SO 内，且 360 新版会做 SO 自校验 + 反调试。
3. 容器是分段压缩+加密（§1.3），不是单块；即便逆出算法也要逐段处理，投入产出比极低。

**离线解密需要补齐的东西（任一）：**
- 用 IDA/Ghidra 反汇编 arm64 的 `DynCryptor::__arm_c_0`，还原解密原语 + 定位 `RMUTGF_KEY` 解出逻辑（需绕过 SO 自校验，工作量以周计，不建议）。
- 或——更实际——直接运行时把内存里已解密的 dex dump 出来（见 §5）。

## 5. 动态脱壳完整操作手册（拿到真机/可控环境即可执行）

> 目标：把运行时被 `libjiagu` 解密、由 `InMemoryDexClassLoader` 加载的真 dex（`com.bxkj.student.*`）dump 成可被 jadx 打开的 dex/jar。

### 5.1 环境准备（先过两道检测）

本 app 有两层检测，启动脱壳前必须处理：
- **模拟器检测**：`com.snail.antifake`（`libemulator_check.so`，`Java_com_snail_antifake_jni_EmulatorDetectUtil_detect`）。
- **Root/调试检测**：广告插件带 `libyaqpro.so`（Payegis 应用加固）、`libturingau.so`（腾讯 Turing 风控）、`assets/libwbsafeedit`。

**推荐路线（最省事）**：真机 + Magisk（Zygisk）+ **Shamiko**（隐藏 root）+ **LSPosed**。Frida 用 `frida-gadget` 注入或 `magisk-frida` 模块，避免被 `TracerPid`/`frida-server` 端口扫描发现。

### 5.2 方案 A：Frida hook InMemoryDexClassLoader（最精准）

360 内存加载真 dex 时必经 `InMemoryDexClassLoader(ByteBuffer[], ClassLoader)` 或 ART 底层 `DexFile.openInMemoryDexFile`。hook 构造参数即可拿到解密后的 dex 字节。

```javascript
// dump_inmem_dex.js  —— frida -U -f com.bxkj.student -l dump_inmem_dex.js --no-pause
Java.perform(function () {
    var counter = 0;
    function dumpBuf(bb) {
        try {
            var Cls = Java.use('java.nio.ByteBuffer');
            var dup = Cls.wrap(bb).duplicate();
            var remaining = dup.remaining();
            var bytes = Java.array('byte', Java.use('java.util.Arrays')
                .copyOf(Java.cast(bb, Cls).array(), remaining));
            var path = '/data/data/com.bxkj.student/dump_' + (counter++) + '.dex';
            var f = new File(path, 'wb'); f.write(bytes); f.flush(); f.close();
            console.log('[+] dumped InMemoryDex -> ' + path + ' size=' + remaining);
        } catch (e) { console.log('dump err: ' + e); }
    }
    // 1) Java 层 InMemoryDexClassLoader(ByteBuffer, ClassLoader)
    var IM = Java.use('dalvik.system.InMemoryDexClassLoader');
    IM.$init.overload('java.nio.ByteBuffer', 'java.lang.ClassLoader')
      .implementation = function (bb, cl) { dumpBuf(bb); return this.$init(bb, cl); };
    IM.$init.overload('[Ljava.nio.ByteBuffer;', 'java.lang.ClassLoader')
      .implementation = function (arr, cl) {
        for (var i = 0; i < arr.length; i++) dumpBuf(arr[i]);
        return this.$init(arr, cl);
      };
});
```

补充：若 360 走 native 直接 `DefineClass`，上面 Java hook 抓不到。此时改 hook ART 的
`art::DexFile::OpenMemory` / `OpenCommon` / `art_LoadDexFile`（用 `Interceptor.attach` 到
`libart.so` 导出符号），从参数取 dex base+size 后 `Memory.readByteArray` dump。各 Android 版本符号名不同，先 `nm -D /system/lib64/libart.so | grep -i opendex` 确认。

### 5.3 方案 B：脱壳机一键 dump（省心）

- **BlackDex**（推荐，免 root 也能跑，自带过部分检测）：装上 BlackDex APP，选 `com.bxkj.student` → 自动 dump 到 `Android/data/.../blackdex_dump_*`，产物直接是 dex。
- **FRIDA-DEXDump**：`python3 main.py -U -f com.bxkj.student`，自动扫内存里所有 `dex\n035` 魔数页并 dump（对分段加载尤其有效）。
- **FART / Youpk**：定制 ROM（基于 AOSP）主动调用每个方法触发 360 的"懒解密"，再整体 dump + 修复（应对函数级抽取/抽取壳）。360 较新版可能用方法抽取，这种情况下 FRIDA-DEXDump 拿到的 dex 方法体可能是空的，需 FART 主动调用补全。

### 5.4 过 com.snail.antifake 模拟器检测

若用模拟器（如 Genymotion/雷电），hook 掉检测函数让它恒返回"非模拟器"：

```javascript
// anti_antifake.js
Java.perform(function () {
    try {
        var E = Java.use('com.snail.antifake.jni.EmulatorDetectUtil');
        // 让 native detect 直接返回 false / 0
        E.detect.overload('android.content.Context').implementation = function (c) {
            console.log('[*] EmulatorDetectUtil.detect bypassed'); return false;
        };
    } catch (e) {}
});
// native 兜底：直接替换导出符号返回 0
var addr = Module.findExportByName('libemulator_check.so',
    'Java_com_snail_antifake_jni_EmulatorDetectUtil_detect');
if (addr) Interceptor.replace(addr, new NativeCallback(function () { return 0; }, 'int', []));
```
更稳的做法仍是**用真机**，绕过 `qemu.*`/`ro.kernel.qemu`/`/dev/socket/qemu` 等一票特征（这些特征字符串在 `libumeng-spy.so` 里也有，见深挖证据）。

### 5.5 dump 后做什么（脱壳的取证目标）

dump 出 dex → jadx 打开 → 重点搜（把"灰产嫌疑"升级成"实锤"）：
1. `com.acse.ottn.*` 的真实代码：无障碍服务 `ShopHelperService` 到底点什么、`CircleFlowService`/`SeedingLoadingActivity` 的导流目标 URL。
2. 电商拉活：搜 `tbopen` / `alibc` / `com.taobao` / `openApp` 在**主 app 代码**里的调用（GDT 插件里已确认有，见深挖证据 §2，但主 app 是否主动调用需脱壳确认）。
3. `libdevInfo`/`libcommonV2DevInfo` 的 Java 调用方，确认采集字段实际上传到哪个接口。
4. `generateAuthInfo`/`auth_*` 的 Java 调用链。
