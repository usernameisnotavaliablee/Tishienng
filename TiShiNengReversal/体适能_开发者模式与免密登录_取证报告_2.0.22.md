### 1.6 打开后到底获得了什么

`isOpenModel()` 全工程只有 2 处消费点，都在 `com.bxkj.base.intercept.e`（全局 HTTP 回调）：

| 位置 | 行为 |
|---|---|
| `e.java:395` `onResponseStart(...)` | 弹「接口信息」对话框：**请求地址 / 请求参数（格式化后）/ 响应状态**，左键**「复制到剪切板」**（`h()`/`i()` 回调 → `ClipboardManager` + toast「已复制到剪切板」） |
| `e.java:221` `onError(...)` | 弹「接口请求报错」对话框：完整异常堆栈，同样可「复制到剪切板」 |

即：**开发者模式 = 明文接口调试面板**（非提权、非改配置）。但对本项目仍有三点意义：

1. 硬编码口令 `396436` 属于可被随意复用的固定凭据，任何拿到 APK 的人都能开；
2. 开启后客户端会把 **接口 URL、全部请求参数（含 token/openid/人脸签名参数）、响应状态** 明文吐到屏幕上并可一键复制 —— 顺带把「参数加密」的对抗成本降到零；
3. 该面板在**未登录的登录页**上就能开，之后所有请求（含登录、上报）全部可读。

对比同文件 `:183` 的正常登录 `D(...)`：

### 2.2 Kotlin 默认值（实锤）

### 2.4 评估

- **[实锤]** 客户端这条请求不携带任何口令，且用当前账号名直接换取新系统会话；成功后 `LoginViewModel.L(map)` 会把 `access_token` / `user_id` / `username` 等写进 `BaseData`（`LoginViewModel.java:1245+`）。
- **[强推断]** 产品意图是「旧系统学校 → 新系统 H5 的单点跳转（SSO）」，服务端以 `type=oldtsn` 识别为可信来源并直接签发。
- **[待验证]** 服务端是否对 `type=oldtsn` 做了来源校验（是否限 IP / 限 `oldToNewH5` 白名单 / 是否只允许该账号属同一学校）。**仅凭客户端无法判定「任意用户名都能登录」**，必须抓包/服务端验证才能定性为越权。这条是该发现能否升级为「认证绕过」的唯一决定点。
- 附带风险面：`H5AppActivity` 的 `username` extra 由 `Bundle` 注入，`JPushReceiver.java:319-330`（sysType==2 分支）会把推送 `extras` 整体 `putExtras` 给 `H5AppActivity`，路径 `:259-330` 亦通过该类。也就是说**服务端推送里带 `username` 即可触发免密登录**（推送通道被控时是放大器）。

### 3.3 评估

- **[实锤]** `123456` 是客户端硬编码的第三方占位口令，并且是**作为 `password` query 参数明文发送**的。
- **[强推断]** 服务端按「第三方渠道 + uid」识别身份，`password` 只是兼容老 `grant_type=password` 表单的填充值；`123456` 可能在该渠道下不参与校验。
- **不一致点（值得单列）**：正常登录 `repository.b.c()`（`:138`）会先 `AESUtils.c(password)` 再 `URLEncoder.encode`，而第三方路径 `repository.b.d()` **完全没加密**。同一 `password` 参数在两条链上编码方式不同 → 说明服务端对第三方路径的 `password` 基本不校验，或该校验形同虚设。
- **[待验证]** 若服务端对某些 uid 回落到常规口令校验，则这些第三方账号的实际口令就是 `123456`。

## 5. 与 Python 项目（`TiShiNengRunning-Github`，自称 2.0.16）的版本差异

| 维度 | APK 2.0.22（本报告） | Python 2.0.16 |
|---|---|---|
| 登录端点 | v2 `POST app/login` / `app/thirdLogin` / `app/autoLogin`（`@Query` 拼 query） | `POST {cloudUrl}/auth/oauth/token`（pom 老网关，`params=`） |
| 认证头 | v2 拦截器体系（`com.bxkj.base.v2.http.*`），口令走 AES-192 `thanks,pig4cloud` | `Authorization: Basic base64(schoolCode + ":pig")`，口令走 `passwordAesUtils` 零填充 |
| `type=oldtsn` | 有 | **未实现** |
| 第三方 `123456` | 有 | **未实现** |
| `396436` 后门 | 有 | 未涉及（属客户端 UI 层） |

即：Python 项目实现的是**老网关 oauth 流程**，本报告三条发现全部落在**新 v2 网关 + 旧 UI**这一代代码上，属于 2.0.22 新增面，二者不冲突。`grant_type=password` 在两套里都是合法值，注意别把本报告里的 `password`（grant_type 值）误当成口令字段。

## 6. 手工复现步骤（静态结论的最小验证路径）

前置：`sysType != 2` 的学校账号（旧系统），或直接取未登录状态。

**A. 开发者模式**

1. 冷启动 → 旧版登录页（大图标 + 表单）；
2. **长按页面顶部 App 图标**（94dp，`mipmap/icon`）；
3. 弹「开发者模式专供开发者调试使用…输入密码」→ 输入 `396436` → 确定；
4. 弹「确定打开开发者模式？」→ 确定；
5. 触发任一接口，观察弹出「接口信息」对话框（请求地址/参数/响应状态），点左键可复制；
6. 校验持久化：`adb shell run-as com.bxkj.student cat shared_prefs/share_date.xml | grep openModel` → `value="true"`。
7. 反证：新版「我的 → 关于我们」（V2 主题）长按图标无任何反应。

**B. `oldtsn` 免密**

1. 登录旧系统账号（`oldToNewH5` 非空，可在 `share_date.xml` 里看到该字段）；
2. 首页九宫格 → **赛事中心**；
3. 抓包过滤 `app/login`，确认请求为 `POST /app/login?username=<账号>&grant_type=password&type=oldtsn`，**无 password**；
4. 观察响应是否直接返回 `access_token` / `user_id`；随后 App 是否直接进入新系统 H5 且不再要求登录。

**C. 第三方 `123456`**

1. 新版登录页（V2）→ 微信 / QQ 登录；
2. 抓包先看 `GET app/thirdCheck?openid=…&type=1|2`；
3. 走到登录时看 `POST app/thirdLogin?username=…&password=123456&grant_type=password&type=wechatlogin|qqlogin`（注意 `qqlogin` 带空格）。

## 8. 结论边界（必须随报告一起对外）

1. 三条发现均为**客户端静态实锤**；**服务端行为一条也没有验证**。发现 2 只有在「服务端对 `type=oldtsn` 不做来源校验」时才是认证绕过，否则仅是产品内 SSO。
2. 未做任何动态验证（360 壳对 Frida Java/native hook 会崩在 `DisableVerifier`，见仓库避坑指南），本报告不含抓包证据。
3. `396436` 的定性应写「硬编码固定凭据 / 明文档口」，不宜写成「远程后门」——其效果限于打开本地调试弹窗。
4. `123456` 的定性应写「客户端硬编码占位口令且未加密上送」，不宜写成「所有第三方账号密码都是 123456」——这取决于服务端是否回落校验。
