## 二、能力测试结论：算法层赢了，密钥层是信息论死局

### 静态攻克的部分（真成果，通常需逆向工程师数天～数周）
- **恢复被 360 蓄意破坏的 ELF**：section header 被改成垃圾使常规工具失效，但 program header + DYNAMIC 完好，自写解析器从中恢复了 20 个命名符号 + 重定位表。
- **逆出加固内部解密原语 = 魔改 RC4**：三处改动（i+=2、j+=S[i]+1、初值 i=3/j=5），逐条汇编坐实，Python 复刻。
- **挖出硬编码密钥** `76 56 57 34 23 91 23 53 56 74`（@0x18a04+0x7456）——推翻了"密钥全在运行时二级 SO"的旧结论。
- **破解 dex 类名索引区 = XOR 0xa6**：解出 appid `7418FDAAB59B1C0C` + 类名 `com.bxkj.student.splash`。

### 静态撞墙的部分（不是能力不够，是数学不允许）
真业务 dex 正文（约 6.8MB 满熵加密）静态不可解。6 种攻击全负结果（魔改 RC4 直解 / keystream 滑窗找内嵌 SO / XOR 周期自相关 / 单字节枚举 / AES 特征 / 已知明文反推）。根因是设计层面的三重屏障：
1. 解密器被 **VMP 指令虚拟化**（符号 `interpreter_wrap_*` 为证），核心逻辑是自定义字节码；
2. 二级加密 SO（`Protect_enc.so` 等）**非磁盘文件**，运行时内存生成（内嵌 ELF 经验证是字符串字面量、GZIP 魔数全假阳性）；
3. 真密钥（`RMUTGF_KEY`）**运行时派生**。

→ 密钥在信息论意义上不在静态文件里。**无论人还是 AI、投入多少算力，纯静态都无法恢复它。**

### 一句话
"以周/月计"对的是**逆算法**这块——Opus 几小时做到了。但 360 的 dex 保护不靠"算法难"，靠"把密钥从磁盘移走"。所以静态解 dex 不可能，**动态脱壳仍是唯一出路**——这是 360 故意留的唯一口子。
