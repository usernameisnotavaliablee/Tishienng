# 本轮(第5轮)纯静态深挖——密钥与算法证据清单

> 环境约束: 无已Root真机, 仅一台 Windows PC。本轮放弃"必须真机脱壳"路线,
> 改攻 360 加固**不保护的明文 native SO** + assets, 用 capstone 反汇编 + ELF 解析。
> 全程本地静态, 未对任何线上服务器发起请求, 未做密钥分解/重打包/分发。
> 证据可复现脚本: tsn\so_recon.py / disasm_so.py / key_hunt.py / global_xref.py

## 1. ★★★ libtsnsecret.so 硬编码 AES 密钥(明文,.data段)

博星自研核心库 `lib/arm64-v8a/libtsnsecret.so`(11.9MB, 静态链 OpenSSL 1.1.1w)。
前几轮只挖到"密钥常量名", 本轮挖出**真实密钥值**:
`.data` 段 0x490010 起 5 个全局指针 → rodata 0x3f1da8 起连续明文:

| 全局符号 | 地址 | 实际值 | 性质/问题 |
|---|---|---|---|
| `AUTH_KEY` | 0x490010 | `165f47a702bf0965d2fb49cdbb373377` | 32 hex = AES-128 鉴权密钥 |
| `WJXY_NFC_KEY` | 0x490018 | `201703141727` | 弱: 形似日期 2017-03-14, 某学院NFC |
| `QR_CODE_KEY` | 0x490020 | `c310d8a21490eddc2f3cd870c34bb732` | AES-128 二维码密钥 |
| `SIGNATRUE_QZONE` | 0x490028 | `ec96e9ac1149251acbb1b0c5777cae95` | AES-128 签名密钥(全库引用最多) |
| `BJYDDXSJXY_NFC_KEY` | 0x490030 | `FFFFFFFFFFFF` | **MIFARE Classic 出厂默认密钥**(北邮世纪学院NFC=等于没设防) |

> 这 5 个 key 在 `JNI_OnLoad` 期由 nlohmann::json 载入配置对象。

## 2. ★★ aes_decrypt 算法 = AES-128-CBC (已坐实)

函数 `_Z11aes_decryptP7_JNIEnvP8_jobjectS2_P11_jbyteArrayS4_S4_` @0x3d973c(10492B, OLLVM平坦化)。
- 签名 = `aes_decrypt(JNIEnv*, jobject, jobject, jbyteArray 密文, jbyteArray 密钥, jbyteArray IV)`
  → 3 个 byte[] 且带显式 IV ⇒ **CBC 模式**(ECB 不需要 IV)
- PLT stub 解析出的 OpenSSL 调用链(证据):
  `EVP_aes_128_cbc → EVP_CIPHER_CTX_new → EVP_DecryptInit_ex → EVP_DecryptUpdate
   → EVP_DecryptFinal_ex → EVP_CIPHER_CTX_free`
- 解密前先调内部 `auth()` 鉴权校验

## 3. rsa_decrypt = 客户端持私钥做信封解密

函数 `_Z11rsa_decrypt...` @0x3ddb90。OpenSSL 错误字符串泄露完整流程:
- 入参含 `privateKeyDer`(PKCS#8 DER 私钥, 由调用方传入)
- `BIO → d2i PKCS#8 私钥 → 提取 RSA → EVP_PKEY_CTX → EVP_PKEY_decrypt_init
  → EVP_PKEY_CTX_set_rsa_padding → EVP_PKEY_decrypt`
- 即: 客户端内置/下发 RSA 私钥, 本地解密服务器下发的密文(信封加密接收端)

## 4. generateAuthInfo = 参数字典序签名

函数 `_Z16generateAuthInfo...` @0x3e2cf0(13080B)。
- 收 Java `Map<String,String>` → 反射 entrySet/iterator/getKey/getValue 遍历
- 塞进 C++ `std::map`(自动按 key 字典序排序)
- `buildKeyValue`(@0x3e11dc) 用 `isalnum`+ostringstream 做 urlencode, 拼 `key=value`
- 经典"参数排序拼接 + 签名"鉴权方案

## 5. ★★★ 快手广告 PNG 隐写整套密钥(本轮最劲爆)

文件 `assets/ksad_common_encrypt_image.png`(2880 字节, 快手 ksad SDK 资源)。
PNG `iTXt` 文本块明文 base64 隐写了**一整套加解密密钥**:

```
[aes_key]         GWL8jXHLnzp63QDH          ← 16字节明文 AES-128 密钥
[rsa_public_key]  MFwwDQYJ...AwEAAQ==       ← 512-bit RSA 公钥
[rsa_private_key] MIIBVAIBADANBgkq...Clxd1Q ← 512-bit RSA 私钥(PKCS#8, 已验证合法DER)
```

问题:
- **512-bit RSA 在 2026 年用普通 PC 即可分解**(早已不安全), 私钥还明文随包分发 ⇒ 形同虚设
- 把私钥隐写进图片 = 安全感错配的"障眼法", 任何人解包即得
- 这是**快手 SDK 自带设计**(非博星自研), 但躺在学生被强制安装的 app 里
- 已提取留证, **未做任何分解或攻击**

## 6. ★★ 博星自研签名校验防重打包链(完全闭环 — 解释了"为何无 Root 难")

调用链(全部静态坐实):
```
aes_decrypt() 解密前  → 调 auth()@0x3cf19c
auth()  → getSignatureByte()@0x14a6ec
            JNI 反射: getPackageManager()
                    → getPackageInfo(getPackageName(), GET_SIGNATURES)
                    → signatures[0].toByteArray()      ← 取 APK 签名证书字节
        → hashByteArray(HASH, ...)                      ← 算 MD5
        → strcmp 比对硬编码 "7F:C0:22:E6:7C:7D:2A:CC:C3:C8:77:0A:46:13:8D:C3"
```

验证(闭环): 该硬编码 MD5 `7fc022e67c7d2accc3c8770a46138dc3`
**= `META-INF/XIAOWEI.RSA` 里 X.509 证书 DER(偏移0x3c, 887字节)的 MD5, 完全匹配**。
即硬编码的就是博星自己证书的指纹。

含义:
- 任何**重打包**(注入 frida-gadget / 改代码后重签名)都会改变签名证书 → MD5 对不上 → `auth()` 失败 → 连最基础的 AES 解密都跑不通
- 这比 360 的完整性校验**更前置**, 是"frida-gadget 免 Root 重打包路线必然失败"的真正根因
- 多个导出变体: `native_auth_5dm`@0x3cfb6c / `native_auth_1ahs`@0x3d015c / `native_auth_652ahs`@0x3d0950 供不同业务点调用

## 方法学要点(给后续窗口)

1. 360 加固**不碰 native SO** → SO 全明文躺磁盘, 无需任何设备即可纯静态深挖
2. 业务函数符号零混淆(C++ mangled 可读), OLLVM 只平坦化控制流, 不混淆符号/字符串
3. **PLT stub 解析**(adrp x16/ldr x17/br x17 → GOT 重定位 → 符号名)是还原静态链 OpenSSL 调用的可靠途径, 优于 GOT-load 寄存器追踪
4. 11.9MB 大 SO 上 capstone 线性反汇编会失步; 从函数边界单独反汇编(`--func`)可靠
5. PowerShell 控制台中文 GBK 报错 → 统一 `PYTHONIOENCODING=utf-8` 或重定向到 txt 再读

## 7. ★第7轮动态验证(unidbg)

第7轮用 unidbg 0.9.9 把 arm64-v8a/libtsnsecret.so 加载进模拟 ARM64 动态执行, 三用例全 PASS(日志 dsh-vm/logs/unidbg_run4.log), 详见《unidbg动态验证报告.md》:

1. **AUTH_KEY** `165f47a702bf0965d2fb49cdbb373377` 以 AES-128-CBC(IV=0) 解出 `TSN-AUTH-TEST-2026` → 印证 §1 密钥值与 §2 算法;
2. **QR_CODE_KEY** `c310d8a21490eddc2f3cd870c34bb732` 同法解出 `QR-CODE-SECRET-42`;
3. **auth() 校验链** 传入真实 XIAOWEI 证书 DER, MD5=`7fc022e67c7d2accc3c8770a46138dc3` 与 SO 硬编码一致 → 解密前置鉴权通过, 印证 §6 "重打包换证书→auth 失败" 结论; generateAuthInfo 输出 `password=abc123&timestamp=1700000000&userName=test`, 印证 §4 字典序拼接。

事实修正: 证书 DER 实为 **891 字节**(§6 旧写 887); 旧 "偏移 0x3c" 指 PKCS#7 `XIAOWEI.RSA` 内位置, 本轮已用 openssl 提取为独立 DER(dsh-vm/cert_xiaowei.der), MD5 一致。
