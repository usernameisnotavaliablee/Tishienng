## 总览

这个 App 是 `com.bxkj.student`，版本 `2.0.22`，从当前脱壳/解密产物看，它不只是校园体育打卡工具。它同时包含：人脸活体、AI 姿态识别、定位/计步、广告联盟、OAID/设备指纹、灰产式无障碍保活组件、设备管理员、防模拟器/Root/Hook 检测、明文 HTTP、热更新通道。最严重的问题是：敏感采集强度很高，但权限、广告和第三方 SDK 面积明显失控。

本报告全部基于本地静态证据，未对线上服务器发请求。

**隐私与权限**：Manifest 里有 58 行权限声明，去重后 41 个权限。明显超出体育打卡必要范围的包括悬浮窗（`SYSTEM_ALERT_WINDOW` / `SYSTEM_OVERLAY_WINDOW`）、后台定位（`ACCESS_BACKGROUND_LOCATION`）、电话/设备信息（`READ_PHONE_STATE` / `CALL_PHONE`）、录音与相机（`RECORD_AUDIO` / `CAMERA`）、装包/保活（`REQUEST_INSTALL_PACKAGES` / `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` / `RECEIVE_BOOT_COMPLETED`）、任务窥探/调度（`GET_TASKS` / `REORDER_TASKS`）、系统级跨用户（`INTERACT_ACROSS_USERS_FULL`）、运动识别（`ACTIVITY_RECOGNITION`）。应用还设置了 `usesCleartextTraffic="true"`，网络安全配置允许明文 HTTP——一个处理人脸、定位、设备指纹的 App 仍允许明文通道，风险很高。

**灰产/权限滥用组件**：最异常的是 `com.acse.ottn`。它注册了一个"购物助手"无障碍服务（`ShopHelperService`，`BIND_ACCESSIBILITY_SERVICE`，`exported=true`），无障碍配置可读取任意窗口内容、模拟手势、截屏、增强 Web 可访问性注入；设备管理员 `MyDeviceAdminReceiver` 带 `force-lock`；多个透明/保活 Activity 和 10 个 exported Service。这套能力不是跑步、体测、人脸核验所需，性质更接近保活、导流、自动点击组件。静态证据能坐实"具备能力"；具体是否、何时实际拉活，还需要动态取证。

**广告与商业 SDK**：静态可见 6 家广告/商业组件（穿山甲/广点通/快手/百度/倍孜/AdScope）+ 抖音直播插件。GDT 插件里还静态存在淘宝/京东唤起能力（`taobao://`、`tbopen://`、`com.taobao.taobao`、`com.jingdong.app.mall`），说明广告 SDK 具备电商导流能力，但不能直接等同于主程序后台主动拉淘宝，触发条件需要动态抓行为。

**设备指纹与反作弊**：不只看定位/步数/人脸，还做设备环境识别——倍孜 `libdevInfo.so` 读取 `boot_id` 和 `/data/data` 时间戳用于反卸载/设备关联；友盟 `libumeng-spy.so` 生成 U-Zid 并检测 Root/模拟器/Xposed/Substrate/QEMU；百度联天 `libliantian.so` 代码路径主动调用读取 eMMC CID、SoC DRM cpuid 等不可重置硬件指纹（实际能否获取取决于设备内核支持）；`assets/na.czl` 解出 59 条模拟器/Root/VM 特征路径。

**加密与接口安全**：`libtsnsecret.so` 暴露了 AES/RSA/签名函数，且存在硬编码密钥、参数字典序签名、APK 签名证书校验防重打包。问题不是"没有加密"，而是"把核心鉴权材料和算法放在客户端 native 里"——客户端一旦被逆向，接口保护就依赖混淆和风控，而不是服务端权限边界。

**第7轮脱壳后的剩余未坐实部分**：`com.bxkj.student` 业务源码与 `com.acse.ottn` 源码已随真业务 dex 脱壳可读（`cap_4`/`cap_8`），此前"待动态取证"的多项已闭环（见 §〇、§4.4）。仍待动态/时序观察的只剩：人脸接口请求体到底上传原图、活体分数还是特征值（Java 层已定位 `app/faceDetect` 加密上传链路，原文/特征值取舍需运行时抓包）；`com.acse.ottn` 落地页最终 URL 明文（onCreate 为 native）；以及长期动态时序观察（实际拉活/导流的真实触发频率）。

**总体判断**：这个 App 的隐私风险不是单点问题，而是"强制校园场景 + 人脸/定位/运动监控 + 多广告 SDK + 灰产无障碍 + 设备指纹 + 明文 HTTP"的组合风险。

## 一、这是什么 App，谁在被迫装它，凭什么红温

「体适能」是博星科技（boxkj.com / tsnkj.com）出品的校园体育类 App，包名 `com.bxkj.student`，主要功能是**校园跑步打卡、体质测试、人脸防代跑/防代考**。它的典型部署方式是：学校把它列为**必装**，跑步里程、体测成绩、平时分跟它绑定，不装就影响学分。也就是说，学生几乎**没有"不同意就不用"的选项**——这正是问题的核心：当一个 App 的安装是被强制的，它对权限、对隐私、对设备控制权的每一次越界，都不再是"用户自愿的交易"，而是**借行政强制力把灰产能力塞进几十万台学生手机**。

## 二、加固与"安全感错配"：360 锁了 Java 层，自研加密库却敞着大门

### 2.1 Java 层：360 加固，纯静态看不到业务码

`classes.dex` 有 **45MB**，但它是个空壳：

```
dex header:  file_size      = 45352584   （= 实际文件大小，被改大以容纳夹带数据）
             class_defs_size = 4          ← 整个 dex 只定义 4 个类
             data_size       = 18180      ← 真正的 dex 数据区只有 18KB
```

那 4 个类全是壳：`com.stub.StubApp`、`com.tianyu.util.Configuration`、`com.tianyu.util.DtcLoader`、`com.tianyu.util.a`。真实业务代码（`com.bxkj.student.*`）被加密成 payload 藏在那 45MB 夹带数据里，运行时由 `assets/libjiagu.so` / `assets/libjiagu_a64.so` 在内存中解密、用 `InMemoryDexClassLoader` 加载。熵分析（dex 切 32 段算香农熵）呈 5~6 为主、穿插 7+ 高熵段，是 360 自有的"分段压缩+加密"容器特征。

入口实锤：`tsn/manifest_decoded.xml` 第 174 行 `android:name="com.stub.StubApp"`。

### 2.1b 把 360 加固本身逆了一遍：自研魔改 RC4 + 明文嵌密钥（本轮新增）

光说"360 加固看不到业务码"还不够。本轮把 `assets/libjiagu_a64.so`（加固运行时）做了一次纯静态逆向，结论是：**连加固层自己的密码学实现都不规范**。

- **故意破坏 ELF，但只破坏得了静态分析层**：360 把 section header 表改成垃圾（`readelf -S`/`nm -D`/IDA 自动分析全部失效），但 program header 和 DYNAMIC 段必须留给系统加载器用，破坏不了。从 DYNAMIC 段即可完整恢复符号表——这种"破坏"挡得住一键工具，挡不住手写解析。
- **核心解密原语是自研魔改 RC4**（非标准密码学）：在标准 RC4 上改了三处——`i += 2`（标准 +1）、`j = j + S[i] + 1`（标准 +S[i]）、初始 `i=3, j=5`（标准 0,0）。逐条汇编已坐实，Python 可复刻。
- **密钥明文硬编码在 .rodata**：`76 56 57 34 23 91 23 53 56 74`（10 字节，@0x18a04 + 立即数 0x7456）。这推翻了"加固密钥都在运行时二级 SO、静态拿不到"的旧判断——至少加固**内部自解密**这层的密钥是嵌死的。
- **dex 类名索引区只用单字节 XOR 0xa6 混淆**：解出来就是 360 appid `7418FDAAB59B1C0C` + 类名 `com.bxkj.student.splash` 等。保护强度近乎没有。

诚实边界：真正的业务 dex 正文（约 6.8MB 满熵加密）**静态解不出**——它走的是另一条 VMP 指令虚拟化 + 运行时内存生成二级 SO（`Protect_enc.so`）+ 运行时密钥派生的链，密钥在信息论意义上不在磁盘里。这部分必须动态脱壳（见 `小米15+MuMu脱壳执行计划.md`）。完整逆向记录见 `tsn/libjiagu逆向技术报告.md`。

> **锐评**：加固厂自己也在"安全感错配"。一个商业加固产品，内部自解密用的是魔改 RC4 这种自研流密码（而非 AES）、密钥还明文嵌在文件里、dex 索引只用单字节 XOR——真正的强度全压在 VMP 和运行时密钥派生上。这说明 360 加固的防线是"难逆但不密码学安全"：它赌的是没人愿意花时间逆 VMP，而不是数学上解不开。对一个被几十万学生强制安装的 App，这种"够用就行"的加固投入，配不上它采集的数据敏感度。

### 2.2 业务层：自研 `libtsnsecret.so` —— 花钱加固，却把锁挂在门外

加固只锁 Java 字节码，**不动 SO**。而博星把全部加解密/签名逻辑放在自研的 `lib/arm64-v8a/libtsnsecret.so`（11.98MB）/ `lib/armeabi-v7a/libtsnsecret.so`（8.59MB），**导出符号完全没混淆**，`nm -D` 一目了然：

```
_Z11aes_decrypt...        aes_decrypt
_Z11rsa_decrypt...        rsa_decrypt
_Z16generateAuthInfo...   generateAuthInfo
_Z16getSignatureByte...   getSignatureByte
_Z5authS...               authS
_Z8auth_sjk...            auth_sjk
_Z15native_auth_5dm...    native_auth_5dm
_Z16native_auth_1ahs...   native_auth_1ahs
native_auth_652ahs        native_auth_652ahs
_Z15formatSignature...    formatSignature
```

更离谱的是**硬编码密钥**——前几轮只看到 SO 里有这些常量**名**，本轮反汇编后发现它们是 `.data` 段（0x490010 起）的全局指针，指向 rodata（0x3f1da8 起）的**明文密钥值**，逐一提取如下：

| 常量名 | 地址 | 明文密钥值 | 性质 |
|---|---|---|---|
| `AUTH_KEY` | 0x490010 | `165f47a702bf0965d2fb49cdbb373377` | 32 hex = AES-128 鉴权密钥 |
| `QR_CODE_KEY` | 0x490020 | `c310d8a21490eddc2f3cd870c34bb732` | AES-128 二维码密钥 |
| `SIGNATRUE_QZONE` | 0x490028 | `ec96e9ac1149251acbb1b0c5777cae95` | AES-128 签名密钥（全库引用最多） |
| `WJXY_NFC_KEY` | 0x490018 | `201703141727` | **弱密钥**，形似日期 2017-03-14 |
| `BJYDDXSJXY_NFC_KEY` | 0x490030 | `FFFFFFFFFFFF` | **MIFARE Classic 出厂默认密钥** |

注意最后一条 `BJYDDXSJXY_NFC_KEY = FFFFFFFFFFFF`——这是 MIFARE Classic 卡**全球通用的出厂默认密钥**。也就是说，对应学院（疑为北邮世纪学院）的 NFC 校园卡读取根本没改默认密钥，等于**没设防**，任何一部 NFC 手机都能读。

**算法也反汇编坐实了**（不再是"看符号名猜"）：

| 函数 | 地址 | 算法 | 依据 |
|---|---|---|---|
| `aes_decrypt` | 0x3d973c | **AES-128-CBC** | 函数签名带 3 个 byte[]（密文/密钥/IV），显式 IV ⇒ CBC；PLT 解析出调用链 `EVP_aes_128_cbc→DecryptInit_ex→DecryptUpdate→DecryptFinal_ex` |
| `rsa_decrypt` | 0x3ddb90 | **RSA 信封解密**（客户端持私钥） | OpenSSL 错误串泄露：load PKCS#8 private key → 提取 RSA → `EVP_PKEY_decrypt_init` → set_rsa_padding → `EVP_PKEY_decrypt` |
| `generateAuthInfo` | 0x3e2cf0 | **参数字典序签名** | 收 Java Map → 反射遍历 → C++ std::map 按 key 排序 → 拼接 |

**还有一道签名校验防重打包**（这是它"杀不死、改不动"的技术底座）：`auth()`@0x3cf19c 在 AES 解密前先调 `getSignatureByte()`@0x14a6ec，通过 JNI 反射 `getPackageManager().getPackageInfo(pkg, GET_SIGNATURES).signatures[0].toByteArray()` 读取 APK 的签名证书，算 MD5，再跟硬编码的 `7F:C0:22:E6:7C:7D:2A:CC:C3:C8:77:0A:46:13:8D:C3` 比对。**已验证**这个 MD5 正是 `META-INF/XIAOWEI.RSA` 里 X.509 证书的 MD5（`7fc022e67c7d2accc3c8770a46138dc3` 完全匹配）。任何重打包改了签名 → MD5 对不上 → 连 AES 解密都跑不通。

编译信息也全留着：OpenSSL `1.1.1w`、`nlohmann/json 3.11.3`、源码工程名 `TsnJNISecret`。

> **锐评**：花钱上 360 加固保护 Java 层，结果把整个密码学体系——AES/RSA 解密入口、签名生成、连**密钥本身**——以未混淆符号 + 明文常量摊在 SO 里。这是教科书级的"安全感错配"：在用户看不见的 Java 层堆防御，在真正的命门（对称密钥、NFC 密钥）上裸奔。尤其 `FFFFFFFFFFFF` 这种默认 NFC 密钥，等于在保险柜上贴了"密码 000000"。
>
> **合规边界（自存档版自守）**：本节列出密钥值作为"硬编码 + 弱密钥"的证据，但**不提供任何用这些密钥/签名构造请求去打 `a.tsnkj.com` 线上服务器的步骤**，不对 512 位 RSA 私钥做分解。提取止于阅读与批评。

凭据：`nm -D --defined-only lib/arm64-v8a/libtsnsecret.so`；`tsn/disasm_so.py` 反汇编（`dis_aes_decrypt.txt` / `dis_rsa_decrypt.txt` / `dis_getSig.txt` / `dis_auth.txt`）；`tsn/global_xref.py` 提取密钥值；MD5 校验对照 `META-INF/XIAOWEI.RSA`。

### 2.3 不止自研库：第三方 SDK 的密钥也在 assets 里裸奔

博星自己的库裸奔也就罢了，包里塞的第三方 SDK 还把密钥藏得"既隐蔽又毫无意义"：

凭据：`tsn/`（`key_hunt`/PNG chunk 解析）；`assets/ksad_common_encrypt_image.png` 的 iTXt 块；`assets/libwbsafeedit*` 的 .rodata（`assets深挖分析.md` 有完整记录）。

## 三、★最劲爆：`com.acse.ottn` 灰产保活/导流组件

这是整个 App 里最不该出现、也最难洗白的东西。`com.acse.ottn` **不是任何一家大厂 SDK**，包名、类名透着一股灰产味：`ShopHelper`（购物助手）、`Excess` / `Excessive`（过量）、`Procree`、`CircleFlow`、`Transparent` / `White` / `Green`（透明/白/绿——典型保活拉活命名）、`Demo`、`Seeding`（种草）。一个校园跑步打卡 App，凭什么集成一个叫"购物助手"的全能无障碍服务？

### 3.1 "购物助手"无障碍服务 `ShopHelperService`

```xml

`force-lock` 名义上是"强制锁屏"，但**设备管理员组件的真正价值在于：一旦被激活，App 就不能被普通方式卸载**（必须先在"设备管理器"里手动撤销）。这是灰产/流氓应用经典的**防卸载提权**手法。校园打卡 App 没有任何理由申请设备管理员。

### 3.3 拉活组件矩阵：透明 Activity + 多进程 Service

`acse.ottn` 在 manifest 里铺了一整排**保活/拉活**组件，全部 `exported="true"` 且大多挂在专门的 `.LoadingActivity` 进程下（节选，`tsn/manifest_decoded.xml` 第 1223–1280 行）：

| 类型 | 组件 | 特征 |
|---|---|---|
| 透明保活 Activity | `TransparentGreenActivity`、`AccessibiltyTsnPermissionGreenActivity` | `excludeFromRecents=true`，"Green"=保活黑话，不进最近任务 |
| 透明拉活 Activity | `ExcessActivity`、`WhiteActivity`、`SeedingLoadingActivity`、`SeedWebViewActivity` | 多种 launchMode，导流/落地页 |
| 监听 | `HomeKeyReceiver`（**空壳**）→ 真实监听为 `m1.java` 动态注册 | HomeKeyReceiver 无 `<intent-filter>`、Java 无 `registerReceiver`；真实监听为 `m1.java` 动态注册 `CLOSE_SYSTEM_DIALOGS`/`SCREEN_OFF` → `finishAndRemoveTask()` |
| 常驻 Service（全 exported） | `MainService`、`TransparentService`、`StartProcreeService`、`CountdownService`、`ExcessService`、`ExcessiveService`、`WebViewService`、`LjFirstService`、`CircleFlowService`、`DemoService` | 承接服务器 `AccessiblityModel` 任务链式启动（非互相复活） |
| WebView 导流 | `WXActivity`、`SeedWebViewActivity`、`WebViewService` | 静默拉网页 |

这套"透明 Activity + 一排互拉 Service + 监听 Home 键 + 无障碍 + 设备管理员"的组合，是**保活/导流黑产的标准件**——它正是这类 App"杀不死、后台偷跑、自己活过来"的根。

> **第7轮深挖修正**：上述组合确实能大幅提高后台存活与导流概率，但"杀不死、自己活过来"的**硬性复活机制在 acse 反编译 Java 层不成立**——无 `startForeground`/`AlarmManager`/`JobScheduler`/`BOOT_COMPLETED`（全树 grep 0 命中），`StartProcreeService` 为空壳。真实保活靠**无障碍系统服务自持 + 多 exported Service + 8 套悬浮窗 + 独立进程 + 诱导开启权限**。见 §3.4/§4.4(d) 与《体适能_脱壳取证_无障碍与保活机制.md》。

### 3.4 关于"开机/电源广播自启动"——这里必须诚实

需要**纠正一个容易写过头的点**：BOOT_COMPLETED、POWER_CONNECTED/DISCONNECTED、BATTERY_LOW/OKAY、TIME_SET、CONNECTIVITY_CHANGE 这些拉活广播，在静态 manifest 里**确实存在**，但它们挂在 **AndroidX WorkManager 的标准组件**上（`androidx.work.impl.background.systemalarm.ConstraintProxy$*`、`RescheduleReceiver` 等，第 1171–1207 行），而且这些 receiver 标注的是 **`enabled="false"`**（由 WorkManager 运行时按需启用）。

`acse.ottn` 自己的 `HomeKeyReceiver`（第 1255 行）在静态 manifest 里**没有写 intent-filter**，且脱壳后核对 Java 层**也没有 `registerReceiver`**（`HomeKeyReceiver.java:149` 仅空 `onReceive`，属**半成品空壳**）。acse 真正生效的 Home/熄屏监听是 **`m1.java` 动态注册** `CLOSE_SYSTEM_DIALOGS` + `SCREEN_OFF`，收到后 `finishAndRemoveTask()` 抹掉自家导流 Activity（`m1.java:409-427/75-77/122-124`）。

> **结论（第7轮脱壳后修正）**：`acse.ottn` 具备完整保活/拉活组件矩阵 = **实锤**；但它**不靠系统广播自启动**——那些 BOOT/电量/时区 action 全属 androidx.work，与 acse 无关。真实保活 = **无障碍系统服务自持 + 10 个 exported Service + 8 套悬浮窗 + 独立进程 + Green Activity 逐项诱导开启权限**；**"被杀后 Java 层自动复活"不成立**（无 `startForeground`/`AlarmManager`/`JobScheduler`/`BOOT_COMPLETED`，全树 grep 0 命中；`StartProcreeService` 为空壳）。本报告不把 AndroidX 的标准广播算到 `acse.ottn` 头上。详见《体适能_脱壳取证_无障碍与保活机制.md》§2。

> **第7轮脱壳修正**：脱壳读到主业务源码后坐实——`com.bxkj.student` 内**无** BOOT_COMPLETED / ACTION_POWER_* / BATTERY_* / TIME_SET / SCREEN_ON 的动态 registerReceiver（grep 0 命中业务自启动广播）；极光推送显式 `JCollectionAuth.enableAutoWakeup(ctx,false)`（App.java:814）。`HomeKeyReceiver` / `MyDeviceAdminReceiver` / `ShopHelperService` 确属"省钱助手"导购 SDK（com.acse.ottn），非主程序自写。故"主程序自启动/偷跑"**不成立（未实锤）**；保活/导流能力集中在 acse.ottn SDK 自身（第三方风险点）。详见《体适能_脱壳取证_业务调用链.md》§5。

凭据：`tsn/manifest_decoded.xml` 第 697、1223–1280 行；`res/uk.xml`、`res/lN.xml`、`res/cq.xml`（`axml_decode.py` 解码）。

> **第7轮脱壳升级**：脱壳读到 `com.acse.ottn` 全量源码后，本节"具备能力"已升级为"主动灰产行为实锤"（无障碍自动点击约 50 个 App、淘客/C2 接口、伪装 APK 静默安装、SSL 校验绕过等），详见新增专节 §4.4(a) 与《体适能_脱壳取证_acse.ottn.md》。

### 6.1 OAID / 设备标识采集

```

这是国内 OAID（匿名设备标识符）联盟的标准接入，向 vivo/小米/华为/OPPO 各厂商索取设备级广告标识。配合 `READ_PHONE_STATE`，App 具备**跨会话稳定标识用户设备**的能力——这正是广告联盟做用户画像/归因的基础。

### 6.2 专职设备指纹采集 SO（本轮反汇编坐实，不再是"嫌疑"）

`lib/arm64-v8a/` 下多个**专职采集设备指纹**的库。本轮逐个反汇编后，采集手段已坐实（前几轮误以为"字符串被加密"，实际并未加密）：

**(a) 反卸载弱指纹**

| SO | 厂商 | 采集内容 | 手段（函数/偏移） |
|---|---|---|---|
| `libdevInfo.so` | 倍孜 beizi | boot_id（开机随机 UUID）+ 安装时间戳 | `getBootMark`@0x13ffc 读 `/proc/sys/kernel/random/boot_id`；`getUpdateMark`@0x143ac 对 `/data/data` 做 `stat()` 取时间字段 |
| `libcommonV2DevInfo.so` | adscope 岩鼠 | /data/data 安装时间戳 | `getDevUpdateMark` 同上 |
| `libumeng-spy.so` | 友盟 U-Zid | zid 设备指纹 | 读 ro.* 属性 + /proc/self，OLLVM 平坦化 |

这些拼成"卸载重装也能弱关联"的反卸载标识。

**(b) ★最严重：永久硬件指纹（卸载/恢复出厂都不变）**

`libliantian.so`（百度联天移动安全风控）的采集**远超上面这些会话级弱标识**：

```
check_vendor / get_cpuid / get_vendor_drm:
  open("/dev/vmdrm0") + ioctl + system("vm -c ...")  直写 MMIO 寄存器
  读 /sys/class/block/mmcblk0/device/cid             读 eMMC CID
→ 采集: eMMC CID（闪存芯片唯一序列号）+ SoC DRM cpuid（芯片级唯一标识）
```

eMMC CID 和 SoC cpuid 是**焊死在硬件上的唯一标识**，刷机、卸载重装、恢复出厂设置都不会变。一个校园打卡 App 通过风控 SDK 读取这种永久硬件指纹，意味着它对设备的标识能力是**终身级**的——你换了系统、清了数据，它依然认得这台手机。

> **精确表述**：`check_vendor` / `get_cpuid` / `get_vendor_drm` 的代码路径是**主动调用** `open("/dev/vmdrm0")` + `ioctl` + `system("vm -c")` 读取 eMMC CID / SoC DRM cpuid，不是探测性调用。实际能否获取值取决于设备内核是否有 `/dev/vmdrm0` 节点（部分 ROM 没有），但代码层面它是主动去读的。

> **诚实标注**：这些库**在 SO 内不含回传域名**（netscan 全 SO 无 http 调用），即"采集动作在 native 完成、结果回吐给各自 Java 层 SDK 上报"。**采集行为已坐实；上报到哪个服务器**需脱壳读 Java 层或动态抓包确认。

> **第7轮脱壳更新（上报去向闭环）**：脱壳读到主业务 Java 层后，设备指纹"采集→组装→上报"链补全——`gank_device_id = android_id→UUID(兜底 getDeviceId/IMEI)`（a0.java:16-86）与百度联天 `LH.getId` 合成 `uniqueCode = MD5(gank_device_id + 联天id)`（f.java:39-64、169-196），作为请求头随**每一个** HTTP 请求上报（y/c.java:210-219），并随人脸/运动加密体上传（通道 B）；服务器域名由 native `Transform.k` 解密（data/b.java:392），Java 层只有密文。→ §6.2 已坐实的"native 采集"与"上报去向"现已由源码闭环（联天 SDK 的 ID 汇入 uniqueCode 上报；eMMC CID/SoC cpuid 是否最终进入 uniqueCode 或单独上报，静态未逐一对应，见附清单）。详见《体适能_脱壳取证_业务调用链.md》§3。
